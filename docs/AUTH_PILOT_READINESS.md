## Registration workspace discovery

`GET /api/workspaces?registration=true` now filters to `isActive=true`, `registrationEnabled=true`, and `type=SCHOOL`. It returns only `id`, `code`, `name`, and `shortName`. CITY and UNIVERSITY_SYSTEM are never public choices; inactive and closed schools are omitted. The service test asserts this scope.

`registrationEnabled` only gates creation of a new account. Login and authenticated access check `isActive`, not `registrationEnabled`. A student at a school under UDN can register before an Award recipient exists; registration has no eligibility query. The existing Phase 3 eligibility gate remains at initial City submission.

The registration UI consumes the same endpoint and sends no `role` or `isActive`. It handles registration closure and workspace refresh. The current UI displays a combined duplicate message for generic `CONFLICT`, so although backend messages distinguish email and student-code conflicts, the form does not yet show separate copy. The frontend checkout was not modified in this backend task.

## Password and session controls

- Passwords use the existing bcrypt `PasswordService`; refresh tokens are persisted as SHA-256 hashes.
- Access and refresh expiration are configurable through `JWT_ACCESS_EXPIRES_IN` and `JWT_REFRESH_EXPIRES_IN` (the checked-in example is 120 minutes and 30 days).
- Refresh rotation uses a conditional update inside a transaction so two callers cannot both consume the same token.
- Admin password reset and account deactivation revoke refresh sessions. Workspace deactivation is checked on login, refresh, and every authenticated request; it does not need a schema change.
- No password or token is written to application audit by the auth flows inspected.
- Email verification and CAPTCHA are not implemented. They were not added in this task.

## Frontend consumer audit

The signup form requests `GET /api/workspaces?registration=true`, renders the safe workspace summary, and submits only student profile fields. Login and signup persist the returned access and refresh tokens in the existing client auth store. Refresh is single-flight in the API client and retries a request once. Logout clears local auth state even if the API request fails. `/api/me` uses the safe-user DTO. Frontend route guards rely on backend active-user/workspace enforcement. Existing browser storage exposes tokens to same-origin JavaScript; this is an existing architecture risk and was not changed here.
